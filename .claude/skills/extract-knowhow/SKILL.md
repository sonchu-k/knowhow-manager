# ノウハウ抽出

渡された資料から「別の案件・別の人でも使える知見」だけを取り出し、誰の・どの会社の話かが分からない形で残す。

目的は2つあり、両方を満たして初めて成功になる。

- **再利用できること**: 元の資料を知らない人が読んで、自分の状況に当てはめて行動を変えられる。
- **特定できないこと**: 読んだ人が、元になった企業・個人・案件を推測できない。

この2つは引っ張り合う。具体性を削りすぎると「コミュニケーションは大事」のような役に立たない一般論になり、残しすぎると出どころが分かってしまう。固有名詞を消し、**構造・因果・判断基準は残す**のが基本方針。

## フォルダの場所

ノウハウの保存先と元資料の置き場は、リポジトリ直下の `knowhow.config.json` で決まる。作業の最初に読むこと。`knowhow.config.local.json` があれば、その値が優先される。

| キー | 意味 | 既定値 |
|---|---|---|
| `knowhow_dir` | ノウハウの保存先(以下「ノウハウフォルダ」) | `knowhow` |
| `inbox_dir` | 処理前の元資料の置き場(以下「元資料フォルダ」) | `inbox` |
| `sensitive_terms_file` | 検出したい固有名詞のリスト(以下「登録語ファイル」) | `.sensitive-terms.txt` |

相対パスは設定ファイルのあるフォルダが基準で、絶対パスや `~` も使える。設定ファイルがなければ既定値を使う。解決後のパスは次のコマンドで確認できる。

```bash
python3 .claude/skills/extract-knowhow/scripts/check_sensitive.py --show-config
```

## 手順

### 1. 入力を読む

渡されたファイル・貼り付けられたテキストを最後まで読む。リポジトリ内で作業している場合、未処理の資料は元資料フォルダに置かれている(git 管理外)。

元資料の内容を、リポジトリ内の git 管理対象の場所へコピーしない。引用もしない。

### 2. 特定情報を洗い出す

抽出を始める前に、資料に含まれる特定情報を把握する。何を特定情報とみなし、どう置き換えるかは [references/anonymization.md](references/anonymization.md) を参照。

名前や社名のような直接的な識別子だけでなく、**組み合わせると特定できる情報**(業界+地域+規模+時期など)にも注意する。

### 3. ノウハウ候補を抽出する

資料の要約ではなく、次のようなものを探す。

- うまくいったやり方と、それが効いた理由
- 失敗・手戻りと、その原因、次に避ける方法
- 判断の分かれ目になった基準(何を見て、どちらを選んだか)
- 繰り返し使える手順・チェック項目・問いかけ
- 事前の想定と実際のずれ

ノウハウとして残さないもの:

- 事実の記録にすぎないもの(誰が何をいつ決めたか)
- その案件でしか成り立たない事情
- 資料に根拠がなく、推測で補わないと書けないもの
- 特定情報を消すと中身が残らないもの

1つの資料から得られるノウハウは0件のこともある。無理に作らず、その場合は理由を添えて「抽出なし」と報告する。

### 4. 一般化して書く

1ノウハウ = 1ファイル。書式は [references/knowhow-template.md](references/knowhow-template.md) に従う。

書くときは、元資料の文章を言い換えるのではなく、資料を閉じた状態で「何を学んだか」を自分の言葉で書き直すつもりで書く。そのほうが言い回しや固有の細部が残りにくい。

数値は、ノウハウの成立に必要な場合だけ、桁感や比率に丸めて残す(「3,480万円」→「数千万円規模」、「17名」→「十数名」)。

### 5. 漏れを確認する

書いた内容を、元資料を知っている第三者の目で読み直す。「これはあの会社の話だ」と分かる手がかりが残っていれば、さらに一般化するか、その部分を削る。

リポジトリ内で作業している場合は機械チェックも実行する。

```bash
python3 .claude/skills/extract-knowhow/scripts/check_sensitive.py
```

引数を省略すると、設定されたノウハウフォルダ全体を確認する。エラーは必ず解消する。警告は内容を見て、問題なければそのままでよい(公開されているツールの公式URLなど)。このスクリプトが拾えるのは形式的なパターンと登録語ファイルの語だけなので、通過しても目視確認の代わりにはならない。

資料に出てきた固有名詞のうち今後も出てきそうなもの(自社名、主要顧客名、製品名など)は、ユーザーに確認したうえで登録語ファイルに追加する。このファイルは git 管理外。

### 6. 既存ノウハウと突き合わせて保存する

ノウハウフォルダの `INDEX.md` と同じカテゴリのファイルを見て、同じ趣旨のノウハウがすでにあるか確認する。

- **同じ趣旨がある**: 新規ファイルを作らず既存ファイルを更新する。新しい適用条件や反例が得られたならそれを追記し、`updated` と `evidence_count` を更新する。
- **矛盾する**: どちらかを消さず、条件の違いとして両方を書く。条件が分からなければその旨を残す。
- **新しい**: `<ノウハウフォルダ>/<カテゴリ>/<短いタイトル>.md` として作成し、`INDEX.md` に1行追加する。`INDEX.md` がまだなければ作る。カテゴリは既存のものを優先し、どれにも合わないときだけ新設する。

ファイル名・カテゴリ名にも特定情報を含めない。

### 7. 報告する

次の内容を簡潔に伝える。

- 追加・更新したノウハウ(タイトルと1行の要旨)
- 取り除いた特定情報の**種類**(「顧客企業名、担当者名、契約金額」など。値そのものは書かない)
- 判断に迷って落としたもの、ユーザーに確認したい点

コミットやプッシュは、ユーザーに頼まれたときだけ行う。

## リポジトリ外(チャットなど)で使う場合

設定ファイルも保存先もない環境では、手順1〜5を行い、テンプレートの書式でノウハウをそのまま回答として出力する。ユーザーがそれをリポジトリへ保存できるよう、推奨のカテゴリとファイル名も添える。機械チェックは実行できないので、手順5の目視確認をより丁寧に行う。
